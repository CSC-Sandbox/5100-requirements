# Feature Evolution: Monitor Data Availability

## What Will the Feature Become?

The Monitor Data Availability feature should evolve into an **independent service** using **both MQTT and REST**.

MQTT makes sense for real-time monitoring because the service can receive data-source activity and publish availability changes as they occur. Other components can subscribe to these changes without continuously requesting status.

REST is useful when another component needs to directly query the current availability of a source or retrieve previously recorded communication failures.

Separating the monitor into its own service also removes the monitoring logic from the current Swing GUI and allows multiple parts of the system to use the same availability information.

## Define the Contract

### 1. Receive Source Activity

The service receives activity messages from the Robot, Gaze, Affect, and LiDAR components.

**Input:**
- Messages generated by Robot, Gaze, Affect, and LiDAR
- The monitor needs the source identifier and the time the message was received

**Input format:**
- MQTT message
- The message data follows the existing `TYPE,data...` format

Examples:

    ROBOT,0.42,-0.18,0.75,...
    GAZE,0.35,0.72
    AFFECT,0.72,0.44,0.65,0.58,0.33
    LIDAR,1.25,-0.40,0.15

**Input interface:**
- MQTT topics such as:

  data/robot
  data/gaze
  data/affect
  data/lidar

The monitoring service does not need to interpret the sensor values. It only needs to know which source sent the message and when it was received.

### 2. Publish Availability Changes

When a source changes between `AVAILABLE` and `UNAVAILABLE`, the service publishes a status update.

**Output:**
- Source identifier
- Current availability
- Timestamp of the change

**Output format:**
- JSON inside an MQTT message

Example:

    {
      "source": "ROBOT",
      "status": "UNAVAILABLE",
      "timestamp": "2026-09-25T14:30:15"
    }

**Output interface:**
- MQTT topic, for example:

  monitor/status

Other components can subscribe to this topic and react when availability changes.

### 3. Query Current Availability

Other parts of the system can request the current communication status of monitored sources.

**Input:**
- Request for all source statuses or one specific source

**Input format:**
- HTTP request

**Input interface:**
- REST endpoints such as:

  GET /monitor/status
  GET /monitor/status/robot

**Output:**
- Current availability of the requested source or sources

**Output format:**
- JSON in an HTTP response

Example:

    {
      "robot": "AVAILABLE",
      "gaze": "AVAILABLE",
      "affect": "UNAVAILABLE",
      "lidar": "AVAILABLE"
    }

**Output interface:**
- REST response

### 4. Query Communication Failures

When a previously available component stops communicating, the monitor records the failure with the affected component and a timestamp.

**Input:**
- Request for recorded communication failures

**Input format:**
- HTTP request

**Input interface:**
- REST endpoint:

  GET /monitor/failures

**Output:**
- Recorded communication failures

**Output format:**
- JSON in an HTTP response

Example:

    {
      "component": "AFFECT",
      "timestamp": "2026-09-25T14:30:15"
    }

**Output interface:**
- REST response

## Identify Dependencies

### Features Used by the Monitor

The monitoring service depends on the features that produce data for:

- Robot
- Gaze
- Affect
- LiDAR

These features provide activity messages. The monitor only uses the source identifier and message arrival time to determine whether communication is still active.

The current Sprint 1 implementation also uses the provided `Broker`. In the next stage, the monitoring logic should depend on a communication abstraction rather than directly depending on `Broker`.

For example, a `MessageSource` interface could allow different implementations to provide messages through:

- the provided Broker
- MQTT
- file playback
- another future communication system

This would allow the communication mechanism to change without rewriting the availability-monitoring logic.

### Features That Use the Monitor

Other features that may use the monitoring service include:

- system health dashboards
- alerting or notification systems
- logging and auditing features
- user interfaces
- other services that need to know whether a component is currently available

These consumers would receive availability changes through MQTT or query current status and failure history through REST.

Using MQTT topics and REST endpoints as the external interfaces keeps consumers from depending directly on the internal Java implementation of the monitor. This allows the monitoring service to be replaced or refactored later as long as the same external contract is maintained.

## Refactoring Opportunities

The current Sprint 1 implementation works correctly, but there are several opportunities to improve its structure as the feature grows.

### Separate Monitoring Logic from the GUI

`MonitorAvailability` currently handles several responsibilities: receiving messages, tracking source activity, detecting timeouts, recording communication failures, and managing the Swing GUI.

A future refactor should separate the monitoring logic from the presentation layer. The monitor should focus on availability and failure detection, while a separate GUI class should only display status information.

This would improve cohesion and better follow the Single Responsibility Principle.

### Reduce Coupling to `Broker`

The current implementation creates and uses the provided `Broker` directly.

A future refactor could introduce an interface such as `MessageSource` so the monitor depends on an abstraction rather than one communication implementation. This would make it easier to replace the Broker later with MQTT, file playback, or another source without changing the monitoring logic.

### Use an Observer-Style Interface for Status Changes

As more components begin using availability information, the monitor should avoid directly knowing about every consumer.

A future Observer-style design could allow listeners to subscribe to status changes. The GUI, logger, alerting system, or MQTT publisher could each react independently when a source changes between `AVAILABLE` and `UNAVAILABLE`.

This would reduce coupling between the monitor and the rest of the system.

### Small Refactoring Implemented

The source identifiers `ROBOT`, `GAZE`, `AFFECT`, and `LIDAR` were previously repeated throughout the class.

They were refactored into constants and a shared `SOURCES` list. Initialization now iterates over that list instead of repeating the same setup code for each source.

This reduces duplicate code, improves naming consistency, and makes the set of supported sources easier to maintain.

### Refactorings Not Needed Yet

Patterns such as Singleton, Factory, Builder, and Blackboard were considered but are not currently necessary.

Adding them now would increase complexity without solving a significant problem. The Observer pattern and a message-source abstraction are the most relevant future improvements for this feature.
